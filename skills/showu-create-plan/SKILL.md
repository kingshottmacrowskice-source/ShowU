# 创建计划（S2）

一次性查找、解释或核对信息，直接答复，不登记模块需求、计划或任务，也不更新完成状态。若用户随后明确要求修改项目或长期遵守某项约定，只对新增的项目要求执行相应流程。

先读 `.showu/brief.md`、`.showu/plans.md`、关联计划和相关代码。brief 属于用户，AI 只读。仓库的需求事实源优先于推测；不从旧版本或聊天摘要猜测已确认需求。

使用相邻的 [S3](../showu-record-requirements/SKILL.md) 比对需求。若发现同模块、同能力点且诉求相斥，立即停止，不创建可执行计划、不修改实现，将冲突交给用户裁决。

无冲突后，在 `.showu/plans/<slug>.md` 写入：目的与用户来源、读过的代码、涉及模块、冲突检查依据、任务复选框、设计理由、验证证据和下一步。slug 使用小写字母/数字/连字符，不覆盖已有计划。初始状态 `status: active`。在 `.showu/plans.md` 的计划表格添加标题、active、相对文件链接。

将确认的需求按模块登记，并标注来源计划/任务。方案偏好与未经确认的建议放设计理由，不能提升为需求。每项任务应有可验证的完成条件。记录现有实现与拟议变更，避免下次会话重做已完成工作。

完成创建后核对索引链接、状态及模块需求来源。后续按 [S1](../showu-update-status/SKILL.md) 更新。若项目尚无 .showu，可建立目录与计划文件，但 brief 由用户提供；不要替用户编造宗旨。

## 规模维护

按项目文件协议的“长期规模与分层”执行；本仓库见 docs/protocol.md，初始化项目见 .showu/protocol.md。只读入口与相关当前内容，历史按需追溯；plans.md 引用的年度索引中也可能有重开的 active/paused 计划。模块代码入口只维护一份，不复制进计划。有效裁决不能藏到历史；归档保留原文、ID 和来源。相关变更结束时核对入口及链接，超过软阈值先复核，不自动删改或拆分。
