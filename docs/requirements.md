## 0. 文档规则（最重要）

1. 只有「**用户明确确认**」或「**用户主动提出**」的内容，才能进入本文档的「已确认需求」。
2. 其余内容一律放在「待确认」区，**不算需求**。
3. 上一版（`../ShowU`）的 `README.md` 与 `docs/REBUILD-SPEC.md` 仅作**背景参考，不是需求**。其中任何细节，除非用户在本次对话中重新确认，否则一律无效。
4. 需求被新增、修改、删除时，都要在「变更记录」留一行。

## 1. 项目定位（已确认）

**唯一宗旨**：制定一套规范，让 AI 在连续数周甚至数月的开发中，始终知道项目为什么存在、当前要做什么、之前为什么这么设计、已经做了什么，并避免与之前的设计冲突。应用和 SKILL 都服务于这一宗旨。

一个**独立应用**（不依赖浏览器）形态的**项目管理文件查看器**，附带**一系列 SKILL**，顺手充当**快捷启动器**和**上下文续接器**。

- 主职能：项目管理文件查看器 + 一系列 SKILL
- 附带职能（「顺便」）：快捷启动器、上下文续接器
- 设计约束：职责单一，避免上一版「职能混乱」的问题
- **第一版范围**：项目管理器（查看器 + SKILL + 启动器 + 基础 git）；上下文续接器、替代桌面为未来预留（见 §4）

## 2. 已确认需求

### 2.1 形态与技术

- **独立应用**，不依赖浏览器（已确认）。
- **技术选型：Tauri 2 + Web 前端**（Vue / React）——A 路线已确认。
- 最低体验：至少要有「**资源管理器**」的感觉（左侧目录树 + 右侧内容区 + 顶部工具栏）。

### 2.2 项目管理文件（总体）

- 格式：**Markdown**（AI 习惯读、git 可 diff、人可读）；JSON / yml 仅用于 `config` 这类固定结构。
- 定位：**主要给 AI 写、给 AI 看**。
- 软件能力：**允许在软件内查看和修改**（非只读）。
- 位置：项目仓库内 `.showu/` 目录，随代码一起进 git。

### 2.3 目录骨架（已确认采纳）

```
.showu/
  brief.md               项目总体介绍（人写，AI 只读）
  plans.md               计划管理文件（登记所有计划）
  plans/<slug>.md        每计划一个任务文件（该计划所有任务 + 状态）
  requirements/<模块>.md 历史需求，按模块分文件
  config.json            固定格式配置
```

### 请求的记录范围

一次性查找、解释或核对信息，直接答复，不登记模块需求、计划或任务，也不更新完成状态。若用户随后明确要求修改项目或长期遵守某项约定，只对新增的项目要求执行相应流程。

### 2.4 计划与任务管理

- 每项目一个**计划管理文件**，登记所有计划；软件内可以**添加、删除计划**。
- **任务管理文件：每个计划一个**，管理该计划下所有任务的状态。
- 每个计划**划分成多项任务**。
- 项目总览支持按计划状态筛选。
- 项目总览的计划列表优先展示未完成计划。
- **状态值（已确认）**：
  - 任务：默认二态复选框 `- [ ]`（未完成）/ `- [x]`（完成）；需扩展时用 `status:` 覆盖 `doing` / `blocked` / `cancelled`。
  - 计划：`active`（进行中）/ `done`（完成）/ `cancelled`（取消）；可选 `paused`（暂停）。

### 2.5 需求管理器

- 记录**历史需求**。
- 分类方式：**按模块分类，不按计划、不按流程**。
- 目的：不同计划的需求触碰到同一逻辑时，能及时发现冲突。
- 冲突检查**前置到创建计划时**（见 §2.8），发现冲突**立刻停止任务**。
- **冲突判定标准（已确认）**：**同模块 + 同能力点 + 诉求相斥**，三条件同时满足才算冲突；仅同模块但不同能力点、或诉求可并存 → 不算冲突；发现冲突 → 停止任务，把冲突摆给用户裁决。

### 2.6 快捷启动器

- 启动 **AI 工具**：claude、DSH、codex 等。
- 启动 **IDE 带目录**：IDEA 等（在指定项目目录打开）。
- **组合启动**：多个 exe / 快捷方式同时启动（例如 clash + chatgpt 同时启动）。

- 配置启动器时可拖入 exe 自动创建启动项，或直接拖入快捷方式；支持拖拽排序、设置启动间隔和并行启动。

- 未选择项目时也可以使用快捷启动器启动程序。

### 2.7 SKILL 清单

| # | SKILL | 职责 |
|---|---|---|
| S1 | 完成状态更新 | AI 完成相关计划或任务后，实时更新计划/任务管理文件，标注完成状态 |
| S2 | 计划创建 | 告知 AI：允许用户描述计划 → AI 为用户创建新的任务管理文件，并把新计划添加进计划管理 |
| S3 | 需求记录 | 告知 AI 在创建计划时登记/比对需求；发现冲突立刻停止任务 |

### 2.8 需求记录 SKILL（S3）规则

- **触发时机：创建计划时**（动手前触发冲突检查，而非完成后——避免「改都改了」才发现冲突）。
- **前置动作：创建计划前，AI 需先读部分代码**，了解项目现状与模块结构，再登记/比对需求。
- **模块清单：自由创建 / 修改**；AI 每次创建计划时可自行新增或修改模块文件。
- **发现冲突 → 立刻停止任务**（不继续执行）。
- 存储：需求按模块归集，每条带「来源计划/任务」标签；操作分新增/变更/冲突三类；不删历史（废弃用状态标记）。

创建计划流程（S2 + S3 组合）：

```
用户描述计划 → AI 先读部分代码 → S3 比对需求
  ├─ 有冲突 → 立刻停止任务（不动手）
  └─ 无冲突 → S2 创建任务文件 + 登记计划 → 开始开发
```

### 2.9 软件侧职责

- **直接读写文件**：软件可直接读写 `.showu/` 文件（添加/删除计划、维护任务、编辑需求等），不经过 AI。
- **项目列表自管**：软件自行管理「有哪些项目」及项目根目录，存软件自身配置，不在项目仓库内。
- **启动器配置自管**：AI 工具命令、组合启动定义由软件自行配置管理。
- **文件监听**：软件监听 `.showu/` 文件变化，自动刷新界面。

- 已添加项目可通过「补全管理文件」补齐缺失的根目录 AGENTS.md 与管理文件。

- 增加首页，以卡片形式显示所有项目。
- 首页项目卡片展示简介文字和几项未完成的计划。

### 2.10 Git 管理（第一版，基础功能）

- 链接仓库；
- 查看远程仓库是否有更新；
- 推送更新（push）；
- 拉取更新（pull）。
- 更复杂的操作（分支 / diff / 提交等）不在第一版范围，见 §4.3。

### 2.11 长期文件规模管理

- 为长期开发制定并实施文件防臃肿方案：采用轻量模块代码入口，控制重复记录，分层组织当前内容和历史，减少默认读取量，同时保留历史及追溯能力。
- 入口关联用于定位，不替代需求冲突检查；不建立逐条需求到全部代码文件的完整映射。
- 具体目录、数量阈值、迁移方式属于计划中的实现设计；已于 2026-11-06 获用户授权实施。

### 2.12 公共工具

允许从本地文件夹或 Git 地址导入公共工具，为各已登记项目分发通知。项目 AI 在下次工作时评估适用性，采用时保存到项目技能目录，完成采用或跳过后清理通知，失败可继续。支持预览后追加项目指令、查看各项目结果和单项目重发。

## 4. 未来 / 非第一版（已明确方向，预留）

### 4.1 上下文续接器

- 方向：**跨 AI 工具的上下文迁移**（例如把 codex 某次聊天的上下文提供给 claude，或把 claude 给 DSH）。
- 状态：**非当前开发重点，预留给未来**。

### 4.2 替代桌面

- 含义：**替代 Windows 桌面的部分职能**，以「项目」的方式管理桌面（而不是一个个文件）。
- 状态：**非当前开发重点，第一版不做**；第一版只需「类似于项目管理器」。

### 4.3 Git 扩展（未来）

- 基础 git（链接仓库 / 查远程更新 / 推送 / 拉取）已在第一版范围（见 §2.10）。
- **更复杂的 git 操作**（分支 / diff / 提交等）留待未来再扩展。
